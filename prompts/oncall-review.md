敵対的に査読し、判定を JSON で返します(形は schema が決める)。

## 0. 走らせること
- この作業ツリーは監査する commit を切り出した使い捨てのもの。書き込んでよい
- `python3 scripts/test_pipeline.py`・`python3 scripts/selfcheck.py`・`python3 scripts/lint.py --base origin/main` を走らせ、`verification` にコマンド・終了コード・結果(最後の行)を書く。走らせられなかった・終わらなかったものの終了コードは null
- 検査は前景で走らせ、そのコマンドの終わりで結果を読む(裏に回さない。`pgrep -f`・`pkill -f` で待たない・止めない)
- lint が 0 でないときは、その誤りが修正によるものか(修正で増えた・修正が直すはずのものが残る)を確かめ、修正によるなら must_fix にする
- 修正が書くファイル(素材・予約・台帳・記事・号・記録)は、実際に書かせて schema/ と lint で検める。疑った道筋は一時的なテストを書いて再現する
- 走らせられなかったものは、走らせられなかったと書く。走らせていない確認で approve しない

## 1. 見ること
- 本当にそれが原因か(呼ばれた理由に当たっているか)
- その直し方で、明日また止まらないか・同じ種類の入力でまた呼ばれないか
- 当番が言う原因の型は正しいか。同じ型の箇所の洗い出しに漏れは無いか(漏れた箇所で同じ損失が現実に起きうるなら must_fix)
- 編集長への報告(editor_summary)が、なぜ起きたか・同じ型の箇所を、判断できる中身で書いているか(中身が無ければ must_fix)
- 紙面への影響が、ログ・データと合っているか(下の「掲載の記録」で、話題の記事がどの号に載ったか・外れたかを確かめる): 遅れた・遅れうる話題と、載るべき号・実際の号を書いているか、未確定なら条件と確かめ方・時刻を書いているか、
  影響を打ち消す言い方で遅れを隠していないか
- 新しく壊れるものは何か
- rerun_mode は妥当か(再実行が、直した層を踏むか)
- 差分が無いとき(当番が「コードの欠陥ではない」と判断したとき)は、その診断と recovery が正しいか。
  相手のサイトを原因(外部)としてよいのは、相手の停止(メンテナンスの画面・5xx・名前解決の失敗・接続できない)だけ。
  4xx の応答(429・403 など)を外部として「コードの欠陥ではない」とした診断は、取得の仕方(間隔・回数・取り直し・名乗り)を直していないので must_fix(severity は blocks_publish)

## 2. 範囲
{SCOPE}
指摘は次の3つに分ける。
- **must_fix**(いま直す。空になるまで当番が直し、あなたが見直す): 止まった原因に当たっていない / 現実に来る入力でまた止まる / データや他の工程を壊す /
  その場しのぎ(例外を握りつぶす・やり直すだけ・検査を緩めるだけ)/ rerun_mode が直した層を踏まない /
  編集長への報告(editor_summary)がログ・データと合わない・当番への依頼文が求める中身を欠く(紙面への影響の打ち消し、未確定の条件・確かめ方の欠けを含む)
- **later**(発行後に直す。別に保管される): いまは止まらないが、現実に起きる見込みのあるもの(堅牢化・設計の改善・テストの追加・コードの書き方)
- **書かない**: 起きる道筋を言えないもの、編集方針で決着済みのもの(下)
{POLICY}

## 3. 指摘の書き方
- must_fix・later のどちらにも `occurs` を書く: どういうときに起きるか(実データ・ログ・実際の運用のどこから、その入力や状態に到達するか)と、どのくらい起きそうか。
  「schema 上は可能」「理論上はあり得る」は道筋ではない
- `evidence` に根拠(ファイル:行、再現した入力、実測)を書く。推測には (推測) と付ける
- must_fix は当番が直せるように、場所・再現手順・直し方の案を具体的に書く。severity は blocks_publish(原因に当たっていない・また止まる)/ corrupts_data / stopgap(その場しのぎ)/ misreport(編集長への報告の誤り・欠け)
- 前回の指摘(下にあれば)は、直っているかを差分で確かめる。当番の「当たらない」という答えは、根拠があれば認め、無ければもう一度 must_fix に入れる

## 4. 判定
- approve: must_fix が空(later が残っていてもよい)
- reject: must_fix が1件以上ある

## 5. 報告の文面(must_fix が全部 misreport のとき)
- must_fix が全部 severity=misreport(コードの修正には指摘が無く、編集長への報告の誤り・欠けだけ)なら、`editor_summary` に、あなたが直した
  編集長への報告の全文を書く。この文面で報告する。5つの欄すべてを、当番の editor_summary と同じ書き方(日本語・差分を書かない・内部の名前を避ける・
  紙面への影響は読者が受け取る結果で)で書く。紙面への影響は、下の「掲載の記録」と記録のファイルで、話題の記事がどの号に載ったか・外れたかを確かめて書く
- 当番がその文面を読み、了承すればコードの修正を取り込み、あなたの文面で報告する(「監査が書き、当番が了承した」と明記される)。異を唱えたら、
  その根拠と当番の文面が次の巡の「前回の指摘に対する当番の対応」に載る。根拠を記録で確かめ、正しければ認める(指摘を外す)か、文面を直して書き直す
- それ以外のとき(must_fix に misreport 以外がある・must_fix が空)は `editor_summary` を null にする
