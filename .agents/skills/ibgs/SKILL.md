# Information Boundary Guard for Spec & Documents

IBG（Information Boundary Guard）の基底原則をビジネス文書・技術仕様書・設計資料の領域へ特化したスキルです。コンテキスト内の「正しい情報」を本来属さない場所へ出力してしまう舞台裏の漏出、運用フェーズや視点の混濁、無印の短文連打による論理放棄、およびLLM特有の定型レトリック（AI Slop）を遮断し、納品物としての構造と情報境界を維持します。

物語執筆には `ibgn`、コラム・批評には `ibge`、対話・議論には `ibgd`、監査・レビューには `ibgr`、翻訳には `ibgt`、エージェント向けプロンプト・仕様設計には `ibgp` を使用してください。

## When to Use

- 規約、ルール、仕様書、README、リリースノート、運用手順書、移行ガイドなどの文書を作成・統合するとき
- 判断根拠、設計書、図解、比較表、稟議書、外注指示書、プレゼン資料などの非創作成果物を生成するとき
- 複数の内部資料、チケット情報、作業指示プロンプトを参照して1つのドキュメントを出力するとき

## Steps

### 1. 出力前に「5つの所属境界」を確定する

情報をすべて同じ作業台に広げて配るのではなく、生成を始める前に成果物の境界を以下の5軸で定義せよ。

1. **誰が書くか（Author Persona / 書き手の主体）**: この文章の視点は誰のものか。「ユーザーの代わり（制定者・設計者・担当者）」か、「依頼を遂行する作業者（AI・受託者）」か、特定の役職か。
2. **誰のために書くか（Target Reader / 最終読者）**: この文章は誰に向けて書かれるか。サービスの利用者か、実装担当者か、運用者か、上司・決裁者か、社外関係者か。読み手がアクセスできる情報と求めている判断基準は何か。
3. **どこに書くか（Document Scope / 置き場所）**: この文書自体の役割は何か（例：ルール本文なのか、改定のお知らせなのか、設計上の判断根拠なのか、運用台帳なのか）。異なるフェーズ・役割の記述を1箇所に混在させない。
4. **何を知っているか（Epistemic Horizon / 知識と時点）**: その読み手や文書が公開・提出される時点で、前提として共有されている情報はどこまでか。
5. **どの基準に属するか（Value System / ドメイン・組織基準）**: その文書が属する組織・プロジェクト・契約上の基準や用語体系は何か。未整理の内部英語識別子と日本語の地の文を無秩序に混交させない。

### 2. 「書き手」と「読み手」のすり替わり（舞台裏の漏出）を遮断する

AIは対話相手である「目の前のユーザー」に向けて、「依頼を遂行する作業者」として親切に報告しようとする習性がある。この視点が成果物に混入することを厳禁とする。

- **「依頼遂行者からユーザーへ」の視点混入を禁止**: ユーザーの代わり（制定者・担当者）として最終読者に向けて書く成果物の中に、「原文ファイルを変更していません」「指示通り統合しました」といった作業者からユーザーへの業務報告を混ぜない。
- **編集方針・プロンプト指示の転記を禁止**: 「個別理由の記載は不要」「簡潔にまとめる」といった作成者向けの編集ルールや指示文を、成果物のテキストや図解の中に印字しない。
- **変更前構造のメタ説明を禁止**: 統合後のルール本文や仕様書の中に「従来のように別ページを見比べる必要はありません」「本資料は一ページで確認できる構成です」といった新旧比較や構成自賛の案内文を混ぜない。案内が必要な場合は、本文とは別の「改定履歴」や「お知らせ」として分離する。

### 3. 内部識別子を最終読者向けの「実質的理由」に翻訳する

外部や最終読者に向けた文書では、「社内のどの案件で管理したか（追跡情報）」と「なぜ変更・決定したのか（実質的理由）」を厳密に区別せよ。

- **内部符号・環境情報の排除**: 社内チケット番号（JIRA等）、内部URL、未公開機能名、内部モジュール構成、デバッグ用隠しオプション、実装者のローカル環境パス（`/Users/...` 等）を読み手が参照できない文書に出力しない。
- **読み手視点への翻訳**: 文脈にチケット番号や内部経緯が根拠として存在しても、そのまま出力せず、その文書の読み手（利用者・上司・下請け等）自身が理解・行動できる理由（例：「誤操作によるデータの上書きを防ぐため、確認手順を追加しました」）へ変換して記述する。

### 4. 短文連打による「接続詞・論理構造の省略」を防ぐ

短文や体言止めを改行で連打して論理関係を省略するのを避け、文と文の関係性が読み手に一目で伝わるように構造化する。行の並びが「単なる羅列」なのか「列挙」なのか「順列」なのか判別できない無印の短文連打を避け、文脈や要素数に応じて以下の4形式から適切なものを選択せよ（ただし要素数が1の単項目の場合は例外とし、無理にリスト化せず通常の文や単一記述として扱う）。

- **助詞・接続詞による散文化**: 因果・背景・内訳・説明として繋がる文脈なら、助詞や接続詞を補って論理が通る文または段落にする。
- **列挙（`*` または `-` で始める箇条書き）**: 順序を持たない複数の同階層要素を並べるなら、`*` または `-` を用いた箇条書きにする。
- **順列（`1.` で始める番号付きリスト）**: 複数の手順、時系列、優先順位、段階的なステップを示すなら、`1.` を用いた番号付きリストにする。
- **ラベル付き記述（`項目名：内容` 形式）**: 属性や詳細項目を対にして示す場合は、`詳細項目：内容` のようなラベル（キー・バリュー）形式を用いる。

### 5. LLM特有の修辞テンプレート（AI Slop構文）を排除する

ビジネス文書や技術資料において、内容を水増しする定型レトリックや過剰な対比構文を排除し、検証可能な事実と論理を中立・明快に記述せよ。

- **「否定＋肯定」の対比構文の反復禁止**: 「単なるXではない。Yだ。」「Xではなく、むしろYである。」といった不要な打ち消しを挟まず、要件や仕様を直接的に記述する。
- **ダッシュ（`――`）による論理接続の代行禁止**: 因果や補足をダッシュで雑に繋がず、適切な接続詞や箇条書きで関係を明示する。
- **定型クロージングの禁止**: 末尾を「ただ一つ確かなことがある。」「今後のさらなる発展が期待される。」といった空疎なまとめテンプレートで締めくくらない。

### 6. 出力直前の検品ゲート（Self-Audit）を通す

成果物を出力する直前に、以下のチェックリストで自己検品を行い、該当する問題があれば修正してから出力せよ。

- [ ] **「誰が」の視点検品**: 書いている視点は適切か？（「ユーザーの代わり」として書くべき場所に、「依頼を遂行する作業者（AI）」としての報告や言い訳が混ざっていないか？）
- [ ] **「誰のために」の宛先検品**: 想定読者（利用者・実装者・上司・顧客など）に向けた文章になっているか？（最終読者ではなく「指示を出したユーザー」に向けた説明になっていないか？）
- [ ] **編集方針の検品**: プロンプトの指示文や編集方針（「記載不要」「省略する」など）が成果物内にそのまま印字されていないか？
- [ ] **置き場所と視点分離の検品**: 作業報告や文書自体のメタ解説が本文に紛れ込んでいないか？ 設計・運用・利用など異なる立場の記述が無秩序に混在していないか？
- [ ] **内部情報の検品**: その読み手が参照できない内部識別子（チケット番号、社内システム名、ローカルファイルパス、ユーザー名）が露出していないか？
- [ ] **論理構造の検品**: 複数要素を並べる際、無印の短文連打にならず「散文」「`*` や `-` の列挙」「`1.` の順列」「`項目：内容` 形式」など関係性が分かる構造になっているか？（単項目の場合を除く）
- [ ] **修辞テンプレートの検品**: 「Xではない。Yだ。」の対比構文、ダッシュによる論理省略、空疎な定型クロージングを使っていないか？

## Gotchas

- **「依頼者（ユーザー）」と「最終読者」を取り違えない**: AIにとって対話相手は常にユーザーであるため、無意識に「AI（作業者）からユーザー（発注者）へのメッセージ」が成果物に漏れ出す。ユーザーの代筆をする際は、AI自身の存在を完全に消し去れ。
- **「親切心」が情報境界を壊す**: AIは「利点を説明しよう」「根拠を明示しよう」「指示を守ったことを示そう」という親切心から舞台裏の情報を漏出させる。説明の丁寧さや情報の正しさよりも、「誰が・誰のために・どこに書く情報か」を常に最優先せよ。
- **自然な文章への警戒**: 境界違反は不自然な文章ではなく、極めて自然でもっともらしい文脈のまま混入する。「文章として自然か」「事実として正しいか」ではなく、「書き手の立場・読み手の属性・置き場所・論理構造が一致しているか」という観点で検品せよ。
